# 代码审查报告

## 项目概述

**jxlsb** 是一个纯 Java 实现的 XLSB（Excel Binary Workbook）格式读写库。核心特性包括：

- **零依赖**：仅依赖 SLF4J 日志门面，无 POI 等重型库
- **堆外内存**：全量堆外内存架构，追求零 GC 压力
- **多版本 JAR**：Java 8 基准实现（ByteBuffer），Java 23+ 自动切换 Foreign Memory API
- **SPI 可扩展**：内存分配器通过 ServiceLoader 自动选择最优实现
- **流式 API**：支持大规模数据流式写入和读取

| 测试依赖 | JUnit 5, Mockito, JMH, POI, EasyExcel, FastExcel |

## 优秀设计

### 1. 零依赖架构与堆外内存

项目仅依赖 SLF4J 作为日志门面，核心业务完全自主实现。堆外内存架构是该项目最突出的设计亮点：

- **MemoryBlock 接口**（`memory.MemoryBlock`）：定义了统一的堆外内存操作抽象，包括 `putByte`/`putInt`/`putDouble` 等小端序写入方法
- **OffHeapAllocator 接口**（`memory.OffHeapAllocator`）：统一内存分配接口
- **SPI 服务发现**（`spi.AllocatorProvider`）：通过 `ServiceLoader` 自动选择最优实现。Java 8 环境加载 `ByteBufferAllocatorProvider`（优先级 10），Java 23+ 环境加载 `MemorySegmentAllocatorProvider`（优先级 20）

这种设计使得库在 Java 8 兼容的同时，能在高版本 JVM 上自动利用更高效的 Foreign Memory API，体现了优秀的前瞻性架构。

### 2. Builder 模式标准化使用

所有公共 API 的构造都使用了 Builder 模式：

```java
XlsbWriter writer = XlsbWriter.builder()
    .template(Path.of("template.xlsb"))
    .path(Path.of("output.xlsb"))
    .build();
```

`CellStyleFormat` 也使用了 Builder 模式，构建链式调用清晰。

### 3. BIFF12 变长编码实现

`Biff12Writer` 和 `VarIntReader` 严格遵循 MS-XLSB 规范实现了变长整数编码/解码：

- `writeVarInt` / `readVarInt`：记录类型编码（高位置 1 表示需要下一字节）
- `writeVarSize` / `readVarSize`：记录大小编码（最多 4 字节）
- 小端序整数/浮点数读写

`Biff12Writer` 中实例级 `intBuffer` 的复用减少了循环内对象创建，是良好的性能优化。

### 4. RK 编码优化

SheetWriter 中的 RK 整数范围判断（`MIN_RK_INTEGER` / `MAX_RK_INTEGER`）允许在 -536,870,912 到 536,870,911 范围内的整数使用 4 字节 RK 编码而非 8 字节 Double，直接贡献了 30-50% 的文件大小缩减。

### 5. 多版本 JAR 架构

通过 Maven 多 Profile（`jdk8`, `jdk23+`）实现 Multi-Release JAR：

- `src/main/java` — 基准实现（Java 8）
- `src/main/java23` — Java 23+ Foreign Memory API 实现
- 对应的 `META-INF/services` 文件分别注册各自提供者

### 6. 流式读取设计

`XlsbReader` 提供了三种读取 API：
- `forEachSheet` — 遍历所有 Sheet
- `forEachRow` — 流式回调处理每行
- `readRows` — 分页批量读取（通过 `BatchCompleteException` 提前终止）

`BatchCompleteException` 作为内部控制流的手段是实现层面的合理选择，对外完全透明。

### 7. 异常体系设计

建立了 `XlsbException(extends RuntimeException)` → `MemoryAllocationException(extends XlsbException)` 两级异常体系。`MemoryAllocationException` 携带了 `requestedSize` 上下文信息，有助于诊断。

### 8. 设计模式总结

| 设计模式 | 使用场景 | 评价 |
|----------|----------|------|
| Builder | XlsbWriter, XlsbReader, CellStyleFormat | 合理，提供流畅 API |
| Factory Method | CellData 静态工厂方法 | 合理，隐藏构造细节 |
| Strategy | OffHeapAllocator 多实现 | 合理，通过 SPI 运行时选择 |
| Adapter | PooledMemoryBlock 包装真实内存块 | 合理，透明增加池化能力 |
| Template Method | BiffRecord.writeTo() 抽象方法 | 合理 |
| Iterator | OffHeapSheet.SheetRowIterator | 实现有缺陷（见问题列表） |

## 包间依赖分析

当前包间依赖关系：

```
api  ────────────────────────► container, format, data
container  ──────────────────► format
format  ─────────────────────► container, memory, data, api
format.record  ──────────────► format, memory, data
format.record.reader  ───────► format, memory
memory  ─────────────────────► (spi 通过 ServiceLoader 间接依赖)
data  ───────────────────────► memory
io  ─────────────────────────► memory
spi  ────────────────────────► memory
exception  ──（独立）
util  ────（独立）
```

存在两处值得关注的依赖：
1. `format → api`：format 包反向依赖 api 包的 `CellData`，违反了分层原则（底层格式层依赖顶层 API 层）
2. `api → data`：API 层暴露了 `data.CellType`，导致用户可以看到内部类型

## 总结

### 综合评价

jxlsb 是一个高质量的 Java XLSB 库，设计上体现了以下几个显著优势：

1. **架构清晰**：包结构职责明确，API/格式/内存/容器分层合理
2. **性能意识**：堆外内存、RK 编码、变长整数、缓冲区复用等优化贯穿始终
3. **兼容性设计**：多版本 JAR + SPI 机制优雅地解决了 JDK 版本差异
4. **API 设计**：Builder 模式 + 流式 API + 模板填充，覆盖了主要使用场景

需要关注的核心问题：

1. **重复代码**（优先级高）：`decodeRk()` 和 SheetReader/SheetParser 的 handler 逻辑存在明显重复
2. **并发安全**（优先级高）：`SharedStringsTable` 的混合锁模式需要统一
3. **API 分层**（优先级中）：`format` 包对 `api` 包的反向依赖需要梳理
4. **静默数据丢失**（优先级中）：`OffHeapCell.setText()` 的截断行为需要显式化
5. **资源管理**（优先级中）：`XlsbFormatReader.SheetContext.reset()` 的异常吞没问题
